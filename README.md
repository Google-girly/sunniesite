# Chapter Admin

Internal admin tool for a sorority/fraternity chapter — originally built
for Sigma Omega Nu, Theta Chapter, and written so any other chapter can
fork it and drop in their own name (see [Forking for your own
chapter](#forking-for-your-own-chapter) below). A sidebar of "modules"
(one per chapter function), and a database each module reads/writes.
This first pass ships the shell plus one real module (**Officer &
Active Roster**) so the pattern is proven before we add the rest one at
a time.

For what's built vs. still to come, see [MODULES.md](MODULES.md).

## Stack

- **Next.js** (App Router, TypeScript)
- **Tailwind CSS v4** — no component library, just utility classes
- **SQLite + Prisma** for the database (local file, zero setup). Swapping
  to Postgres/Supabase later is a config change, not a rewrite — see
  [Database](#database--swapping-to-postgres-later) below.
- **Shared-password auth** — one password for the whole exec board, no
  individual accounts yet. See [Auth](#auth) below for exactly what that
  means and doesn't mean.

## Getting started

```bash
npm install              # installs deps + generates the Prisma client
cp .env.example .env     # then edit .env: set your own APP_PASSWORD
npx prisma migrate dev   # creates prisma/dev.db and applies the schema
npm run dev              # http://localhost:3000
```

You'll land on `/login`. Enter whatever `APP_PASSWORD` you put in `.env`.

## Forking for your own chapter

This repo has no chapter-specific data checked in — everything below is
config, not code changes:

- **Name/branding** — set `NEXT_PUBLIC_CHAPTER_ORG_NAME` and
  `NEXT_PUBLIC_CHAPTER_LABEL` in `.env` (see `.env.example`). Every page
  that shows a chapter name (sidebar, login, dashboard, meeting-minutes
  exports/emails) reads from `lib/chapterConfig.ts`, which reads those
  two vars — nothing to find-and-replace in source.
- **Calendar** — set `NEXT_PUBLIC_CHAPTER_CALENDAR_ID` to your own
  Google Calendar's id (Settings → Integrate calendar → Calendar ID).
  See `lib/calendar.ts`.
- **Letterhead** — Chapter Standards letters and the Event Report export
  reuse the crest/header baked into
  `lib/templates/event-report-template.docx` (see `lib/docxLetterhead.ts`).
  That's real artwork inside a binary Word file, not something an env
  var can swap — replace that one template's header/crest in Word with
  your own chapter's letterhead and every export built on it picks up
  the change automatically.
- **Other `lib/templates/*` files** (Financial Books, Community Service,
  Study Hours, Standards Forms, Pledgeship) are your chapter's own blank
  forms — swap in your chapter's real templates the same way.
- **Auth/roster/database** — a fresh `npx prisma migrate dev` starts you
  with an empty database; nothing from the original chapter is bundled.

## Auth

Logging in checks the password you typed against `APP_PASSWORD` in
`.env`. On success it sets an `httpOnly` cookie holding a hash of that
password. `proxy.ts` checks that cookie on every request and bounces you
to `/login` if it's missing or wrong. Logging out just clears the
cookie.

That's it — there's no user table, no per-person permissions, no "who
did this" tracking. Everyone with the password has full access to
everything. That's a deliberate simplification for a small trusted exec
board on localhost, **not** something to expose on the open internet as-is.
Before this app is ever deployed somewhere reachable outside the board,
swap this for real per-user accounts (a `User` model + a proper auth
library, e.g. NextAuth/Auth.js) — flagging that now so it doesn't get
forgotten later.

## The module pattern

Everything under `app/(app)/<name>/` follows the same shape: a Prisma
model (or a few), a couple of API routes, a server page that loads the
initial data, and a client component that handles interactivity. The
roster module is the reference implementation for a flat, single-table
module — when adding one of those, open its files side-by-side with the
steps below. For a module with real nesting (a record with sub-records
of its own, e.g. an event with two budget versions each with their own
line items), Budgets (`app/(app)/budgets/`) is the reference instead —
same steps, just one more model per level and routes nested to match
(`app/api/budgets/[id]/versions/[versionId]/items/...`).

**Say we're adding a `fines` module. Here's the walkthrough:**

1. **Add the model(s) to `prisma/schema.prisma`.**
   Copy the shape of the `Member` model — an `id`, whatever fields the
   module needs, `createdAt`/`updatedAt`. If a field has a fixed set of
   options (like roster's `status`), make it a `String` (not a Prisma
   `enum` — SQLite doesn't support those) and keep the allowed values in
   a `lib/<module>.ts` file, the way `lib/roster.ts` does.

2. **Run the migration.**
   ```bash
   npx prisma migrate dev --name add_fines
   ```
   This updates `prisma/dev.db` and regenerates the client in
   `app/generated/prisma/`.

3. **Add API routes.**
   - `app/api/fines/route.ts` — `GET` (list) and `POST` (create)
   - `app/api/fines/[id]/route.ts` — `PATCH` (update) and `DELETE`

   Copy `app/api/roster/route.ts` and `app/api/roster/[id]/route.ts` as
   your starting point and swap `prisma.member` for `prisma.fine`.

4. **Build the page.**
   - `app/(app)/fines/page.tsx` — a server component that does
     `await prisma.fine.findMany(...)` and passes the result into a
     client component as `initialMembers`-style props.
   - `app/(app)/fines/FinesClient.tsx` — a `"use client"` component
     with the table + add/edit form, calling the API routes from step 3.
     Copy `RosterClient.tsx` and adjust the fields.

5. **Flip the switch in `lib/modules.ts`.**
   Find the `fines` entry and change `status: "planned"` to
   `status: "active"`. The sidebar "Soon" badge disappears and the
   dashboard card starts linking to real content automatically — nothing
   else to wire up, since the nav already points at `/fines`.

6. **Delete the placeholder page's old content.**
   `app/(app)/fines/page.tsx` currently renders `<ModulePlaceholder>`.
   Step 4 replaces that file's contents entirely.

7. **Check `MODULES.md`.**
   Tick the module off the roadmap.

That's the whole pattern — every future module (Fines, Pledgeship,
Community Service, Meetings & Reports, Standards Forms, and whatever
else comes up) follows these same seven steps.

### Rollup / derived modules

Not every module needs its own model. **Chapter Finances**
(`app/(app)/finances`) is a "live view" module: it has no schema, no
migration, no API routes, and no client component — its `page.tsx` is a
server component that queries `prisma.budget.findMany` for each event's
`FINAL`-stage `BudgetVersion` and renders the rollup directly. This is
the pattern any time a module's whole job is "show data that already
lives in another module, combined or summarized" — resist the urge to
copy the data into a new table just to have somewhere to display it.
Copying it would mean writing sync logic (and it *will* drift, the
first time someone edits the original and forgets the copy). Querying
the source tables directly means there's nothing to keep in sync: edit
a Final Budget, refresh Chapter Finances, the number's already right.

### Exporting into a real template

Some modules exist to replace paperwork the chapter already submits in a
specific file format (Standards Forms, Event Reports). For those, "the
data lives in the app" isn't quite enough on its own — you also want a
real file back out, in the chapter's actual template, not a lookalike.

Budgets does this (see the "Export to Excel" button on a Tentative/Final
budget's own page) and is the reference for how to do it again:

1. Put a copy of the real template in `lib/templates/`.
2. Open it once with [ExcelJS](https://github.com/exceljs/exceljs) in a
   throwaway script and dump every row/cell/merge — don't guess cell
   addresses from what the labels look like. Real chapter spreadsheets
   accumulate copy-paste quirks over the years (mislabeled cells, a
   formula on one sheet that isn't on its sibling sheet); reading the
   actual file catches those before they become bugs in the export. This
   step is just for reading — ExcelJS is a devDependency-style tool here,
   not something the app ships with (see step 3).
3. Write a `build<Thing>Workbook()` function (see `lib/budgetExport.ts`
   and `lib/financialBooksExport.ts`) that edits the template's XML
   **directly**, cell by cell, using [JSZip](https://github.com/Stuk/jszip)
   — find each target cell's `<c r="REF">` element with a regex and swap
   in the new value, keeping everything else (styles, merges, borders,
   the other sheets) byte for byte untouched. Don't load the whole
   workbook through a library that reparses and rewrites it (we tried
   ExcelJS's read → modify → write for this and it silently renumbered
   the style table on every save, which broke borders on merged boxes
   like the letterhead and the NVP Finance box — passed every structural
   check yet still looked wrong once opened). Leave formula cells alone —
   Excel/Sheets recalculates them on open, especially with
   `fullCalcOnLoad="1"` patched into `workbook.xml`'s `<calcPr>` before
   writing. The actual cell-editing helpers
   (`patchCell`/`patchCells`/`resolveSheetPath`/`cellHasValue`/
   `forceFullCalcOnLoad`) live in `lib/xlsxPatch.ts`, shared by both
   exporters — pull from there rather than re-deriving them a third time.

   If the target file is a **growing document someone already maintains**
   (not a static form you fill in once, like Budgets' export, but a real
   ledger with its own history — Financial Books' "Budget Log" sheet is
   the example), don't try to *insert* rows: real workbooks like this
   tend to have every row already pre-styled far past the used range
   (blank `<row>` elements with correct borders/number formats sitting
   there unused), so find the first genuinely blank one (`cellHasValue()`
   in `lib/xlsxPatch.ts`) and fill in from there instead. Regenerate the
   whole appended block from the source-of-truth data every time rather
   than building on top of a previous export's output — that's what
   makes repeat exports safe to click: identical app data always
   produces identical rows in the same place, so nothing is ever
   duplicated, and the document's real pre-existing history above the
   appended rows is never touched.
4. Add a `GET /api/<module>/[id]/export` route that calls it and returns
   the bytes with `Content-Disposition: attachment`.
5. If deploying: add the template path to `outputFileTracingIncludes` in
   `next.config.ts` (already done for budgets) so it ships with the
   build — it's read off disk at runtime, not imported, so Next's
   bundler wouldn't otherwise know to include it.

## Database & swapping to Postgres later

Right now `DATABASE_URL` in `.env` points at a local SQLite file
(`prisma/dev.db`), which is why local dev needs zero external accounts.
When it's time to deploy:

1. Get a Postgres connection string (e.g. from Supabase).
2. In `prisma/schema.prisma`, change `provider = "sqlite"` to
   `provider = "postgresql"`.
3. Swap the driver adapter in `lib/prisma.ts` (currently
   `@prisma/adapter-better-sqlite3`) for `@prisma/adapter-pg` or
   Supabase's recommended adapter.
4. Update `DATABASE_URL` to the Postgres connection string.
5. Run `npx prisma migrate deploy` against the new database.

The rest of the app (schema shape, API routes, pages) doesn't change —
Prisma is the layer that's meant to absorb this swap.
